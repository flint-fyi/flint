TypeScript's `import type` syntax marks imports that exist only for type checking.
Those imports are removed from emitted JavaScript without requiring the transpiler to understand the imported module's types.

This rule reports regular imports when every used imported binding from that declaration is referenced only in type positions.

## Examples

### Type-only named imports

<Tabs>
<TabItem label="❌ Incorrect">

```ts
import { User } from "./types";

type Admin = User & { isAdmin: boolean };
```

</TabItem>
<TabItem label="✅ Correct">

```ts
import type { User } from "./types";

type Admin = User & { isAdmin: boolean };
```

</TabItem>
</Tabs>

### Mixed type and value imports

<Tabs>
<TabItem label="❌ Incorrect">

```ts
import { User, createUser } from "./users";

type Admin = User & { isAdmin: boolean };
const user = createUser();
```

</TabItem>
<TabItem label="✅ Correct">

```ts
import type { User } from "./users";
import { createUser } from "./users";

type Admin = User & { isAdmin: boolean };
const user = createUser();
```

</TabItem>
</Tabs>

### Default and namespace imports

<Tabs>
<TabItem label="❌ Incorrect">

```ts
import User from "./types";

type Admin = User & { isAdmin: boolean };
```

```ts
import * as Types from "./types";

type Admin = Types.User & { isAdmin: boolean };
```

</TabItem>
<TabItem label="✅ Correct">

```ts
import type User from "./types";

type Admin = User & { isAdmin: boolean };
```

```ts
import type * as Types from "./types";

type Admin = Types.User & { isAdmin: boolean };
```

</TabItem>
</Tabs>

## Options

### `prefer`

`prefer` controls whether the rule expects type-only imports or regular imports for bindings used only as types.
It defaults to `"type-imports"`.

- `"type-imports"` reports regular imports that are used only as types.
- `"no-type-imports"` reports `import type` declarations and inline `type` import specifiers.

Examples of incorrect code with `{ prefer: "no-type-imports" }`:

```ts
import type { User } from "./types";

type Admin = User & { isAdmin: boolean };
```

```ts
import { type User, createUser } from "./users";

type Admin = User & { isAdmin: boolean };
const user = createUser();
```

### `import()` type annotations

`import()` type annotations are always reported.
Use top-level `import type` declarations instead.

Examples of incorrect code:

```ts
type User = import("./types").User;
```

```ts
let value: import("./types").User;
```

### `fixStyle`

`fixStyle` is accepted for compatibility with equivalent rule configurations.
Flint does not currently provide a fixer for this rule, so both `"separate-type-imports"` and `"inline-type-imports"` report the same imports.

## Decorator Metadata Caveat

When a file contains decorators and the TypeScript compiler options enable both `experimentalDecorators` and `emitDecoratorMetadata`, TypeScript can emit runtime metadata for types that appear only in type annotations.
In that configuration, this rule does not report import declarations from decorated files because changing those imports to `import type` can change emitted decorator metadata.

## When Not To Use It

If your project intentionally keeps type-only dependencies in regular imports, configure `{ prefer: "no-type-imports" }` or disable this rule.
If your project already relies on TypeScript's `verbatimModuleSyntax` errors for import consistency, you may not need this rule because the compiler will reject many of the same import forms.
