TypeScript allows specifying a `type` keyword on exports to indicate that the export exists only in the type system, not at runtime.
This makes it more clear that the exports are type-only, which helps clarify code and also allows transpilers to drop exports without knowing the types of the dependencies.

Using `type` on exports can be preferable in many project setups.
This rule can be enabled to enforce that if something is a type-only construct, such as an `interface`, any exports of it must be `export type`.

## Examples

### Type-Only Re-exports

<Tabs>
<TabItem label="❌ Incorrect">

```ts
import type { User } from "./types";
export { User };
```

</TabItem>
<TabItem label="✅ Correct">

```ts
import type { User } from "./types";
export type { User };
```

</TabItem>
</Tabs>

### Inline Type Imports

<Tabs>
<TabItem label="❌ Incorrect">

```ts
import { type Post } from "./types";
export { Post };
```

</TabItem>
<TabItem label="✅ Correct">

```ts
import { type Post } from "./types";
export type { Post };
```

</TabItem>
</Tabs>

## Options

This rule is not configurable.

## When Not To Use It

If you use [TypeScript's `--isolatedModules` compiler option](https://www.typescriptlang.org/tsconfig/isolatedModules.html), the type checker will error if a type is not re-exported using `export type`.
This rule may be less useful in those cases.

If you specifically want to use both export kinds for stylistic reasons, or don't wish to enforce one style over the other, you can avoid this rule.
Many projects, such as those using bundlers like Vite and Webpack, don't need explicit `export type`s.
Those projects may prefer omitting the `type` from `export`s and/or `import`s for brevity.

Keep in mind that inconsistent style can harm readability in a project.
We recommend picking a single option for this rule that works best for your project.
