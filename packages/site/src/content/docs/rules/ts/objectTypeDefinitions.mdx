TypeScript provides two ways to define named object types: interfaces and type aliases.
While they are largely interchangeable for simple object types, interfaces have some unique characteristics that can be beneficial.

Interfaces support declaration merging, which allows extending an interface across multiple declarations.
They can also be implemented by classes using the `implements` keyword, providing clearer contracts.
Additionally, TypeScript compiler error messages tend to display interface names directly, making debugging easier.

This rule reports type aliases that define object literal types, suggesting the use of interface declarations instead.

## Examples

<Tabs>
<TabItem label="❌ Incorrect">

```ts
type Person = { name: string; age: number };
```

```ts
type Config = {
	host: string;
	port: number;
};
```

```ts
export type UserSettings = { theme: string };
```

```ts
type Generic<T> = { data: T };
```

</TabItem>
<TabItem label="✅ Correct">

```ts
interface Person {
	name: string;
	age: number;
}
```

```ts
interface Config {
	host: string;
	port: number;
}
```

```ts
export interface UserSettings {
	theme: string;
}
```

```ts
interface Generic<T> {
	data: T;
}
```

```ts
type StringAlias = string;
```

```ts
type Union = TypeA | TypeB;
```

```ts
type Intersection = TypeA & TypeB;
```

```ts
type Mapped<T> = { [K in keyof T]: T[K] };
```

</TabItem>
</Tabs>

## Options

This rule is not configurable.

## When Not To Use It

Type aliases and interfaces have subtle differences that may make type aliases preferable in some scenarios:

- Type aliases can represent union types, intersection types, tuples, and other complex types that interfaces cannot directly express.
- Type aliases are often preferred in codebases that use a functional programming style.
- When you explicitly want to prevent declaration merging, type aliases ensure the type cannot be accidentally extended elsewhere.
- Some teams prefer the visual consistency of using `type` for all type definitions.

If your team has established conventions that favor type aliases for object types, or if you're working in a codebase that consistently uses type aliases, you may want to disable this rule.
